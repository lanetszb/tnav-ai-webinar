AI in tNavigator 26.2

Your question first: where does the model run?

Internal
1 · Built-in AI Assistant
What is itThe AI that ships inside tNavigator. Nothing extra to install.
What it can doAnswers questions, generates workflows, explains calculation logs.
Can it stay local?Yes, always. The model runs on your hardware; data never leaves your environment.
Internal
2 · AI Assistant + external model
What is itThe same Assistant pointed at any OpenAI-compatible endpoint you configure.
What it can doThe same tasks, with a stronger model.
Can it stay local?Yes, if you host the endpoint on-prem (Ollama exposes one). No, if you point it at a third-party cloud.
External
3 · AI agent via Local MCP Server
What is itAn outside agent (Claude, Codex, OpenCode) driving tNavigator directly.
What it can doBuilds models, runs simulations, matches history, writes reports.
Can it stay local?Yes: OpenCode + Gemma via Ollama, all on one workstation. No, with cloud agents like Claude.
In every configuration the MCP server and all tNavigator execution stay on your machines; only the model placement varies. The practical trade-off: frontier cloud models are currently markedly stronger for agentic, multi-step work than local open models.

Case study · August 2026

Legacy GAP/PROSPER network → tNavigator, without an IPM license

The task

A 15-well gas network with material-balance tanks, built in GAP v14.5 / PROSPER — and no IPM license available to open it.
tNavigator's ND import brings topology and VFP/VLP, but the well IPRs don't survive the import.
The text exports turned out to be stale templates: the only source of truth was the binary .Out / .gap files.

What the agent did

Reverse-engineered the binary format and extracted full 20-point IPR tables, Jones coefficients and well-test points for all 15 wells.
Verified digit-exact against PROSPER reports opened by the engineer: 3 wells checked, 3/3 exact on every value.
Caught real issues: stale cached tables one generation old, and single-test IPRs extrapolated far beyond data — flagged for engineering review.

Takeaways · next step

Fully local is a config choice, not a rebuild

  • Data locality: the MCP server and all tNavigator execution always stay on your machines; a fully local agent (OpenCode + Gemma via Ollama) is supported today.
  • Capability trade-off: frontier cloud models are currently markedly stronger for agentic, multi-step engineering work.
  • Suggested POC path: start with a strong cloud model on a non-sensitive project to see the ceiling; switching to fully local afterwards is a configuration change.
